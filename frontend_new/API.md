# Що frontend очікує від твого бекенду

Нових обов’язкових ендпоінтів для дашборду немає: він уже сумісний з твоїми `GET /api/latest`, `GET /api/hourly` і `GET /api/daily`. Формат `label` можна залишити: frontend ігнорує його та форматує `time`/`start` самостійно.

Час — рядок RFC 3339 з часовим поясом, бажано UTC (`Z`). Числа — JSON number, не рядки; `null` означає відсутність значення, нуль є справжнім виміром. Вологість — 0–100 включно. Для добових записів `start` — справжній початок дня в обраній зоні, не час формування відповіді. JSON приклади нижче описують формат, а не реальні показники.

## Уже потрібні маршрути

### `GET /api/latest`

Призначення: останній вимір, навіть якщо він давній.

```json
{"temp":20.4,"humid":58.2,"time":"2026-10-29T12:30:00Z"}
```

Без жодного запису: `200` з `null`. Значення окремого несправного каналу може бути `null`; час залишається обов’язковим. Фронтенд сам перевіряє свіжість. Не замінюй timestamp на поточний час під час читання.

Функція для самостійної доробки: `GetLatestData` має розрізняти «таблиця порожня» та помилку БД; handler повертає `null` у першому випадку і `500` у другому.

### `GET /api/hourly`

Призначення: сирі виміри за ковзні останні 24 години. Назва збережена для сумісності; поточна реалізація не агрегує погодинно.

```json
[
  {"start":"2026-10-29T12:00:00Z","temp":20.1,"humid":59.0},
  {"start":"2026-10-29T12:30:00Z","temp":20.4,"humid":58.2}
]
```

Порожня історія: `200` з `[]`. Рекомендований порядок — від старих до нових; frontend додатково сортує. Не додавай синтетичних нулів або вимірів. Фронтенд не передає `hours`, оскільки твій поточний handler його не обробляє.

Функція: `GetHourlyData` читає вікно `[now - 24h, now]`. Для стабільної вибірки збережи один `now` на весь запит.

### `GET /api/daily`

Призначення: середні температури та вологості за сьогодні й шість попередніх календарних днів у `Europe/Kyiv`.

```json
[
  {"start":"2026-10-28T00:00:00+02:00","temp":20.2,"humid":57.8,"count":48},
  {"start":"2026-10-29T00:00:00+02:00","temp":20.6,"humid":56.4,"count":26}
]
```

`count` необов’язковий, позначає фактичні записи в групі, не очікувані. День без вимірів можна пропустити або повернути з `temp:null, humid:null, count:0`. Повністю порожня історія: `[]`. Поточний frontend розуміє обидва варіанти.

Функція: `GetDailyData` обчислює денні середні. Використовуй межі `[start, nextStart)`, щоб опівніч не потрапляла у два дні. `nextStart` — наступний календарний день у зоні, а не завжди `start + 24h` через перехід літнього часу. Не покладайся на локальну зону ОС сервера.

## Помилки

Для всіх маршрутів: `Content-Type: application/json; charset=utf-8`. Відсутність вимірів — успішна порожня відповідь; недоступність БД — `500`:

```json
{"error":{"code":"database_error","message":"Не вдалося прочитати виміри"}}
```

Не повертай SQL чи внутрішні шляхи клієнту. Frontend показує стан помилки за HTTP-статусом, не вставляє текст відповіді у HTML.

## Що варто самостійно виправити в наявному Go-коді

Це рекомендації; жоден Go-файл не змінювався.

1. `getData`: робити паузу/повтор із затримкою після мережевої помилки. Зараз `continue` обходить `Sleep` і створює цикл без затримки.
2. Закривати `resp.Body` на кожній гілці, включно з помилкою JSON; перевіряти HTTP-статус до декодування.
3. Перевіряти довжину `Temp`/`Humid` та типи перед `[0].(float64)`, щоб погана відповідь датчика не зупинила процес.
4. Повертати помилки з функцій БД до handler замість `panic`/`log.Panic`; окремо обробляти `sql.ErrNoRows`.
5. Перевірити ініціалізацію схеми БД: `CreateMainTable` є, але `main` її не викликає. Продумати створення таблиці при першому запуску.
6. Для щоденних середніх виправити часову зону й включення правої межі `BETWEEN`.

## Необов’язкові навчальні розширення

Їх ще не викликає цей frontend. Можеш реалізувати пізніше та під’єднати.

### `GET /api/status`

Функція `GetSensorStatus`: показати успішне опитування та окремо останню спробу. Це дасть змогу відрізняти працюючий API від працюючого датчика.

```json
{"last_attempt_at":"2026-10-29T13:00:00Z","last_success_at":"2026-10-29T12:30:00Z","sample_interval_seconds":1800,"status":"stale"}
```

`status`: `ok`, `stale`, `unavailable`. Часи можуть бути `null`, якщо спроб/успіхів ще не було. Чітко визнач у себе поріг stale.

### `GET /api/summary?period=24h`

Функція `GetSummary`: точні min/max/avg за всіма сирими вимірами, кількість та межі періоду. Це корисно, якщо історія надалі стане агрегованою й frontend уже не зможе правильно порахувати екстремуми сам.

```json
{"from":"2026-10-28T13:00:00Z","to":"2026-10-29T13:00:00Z","count":48,"temp":{"min":18.3,"max":22.1,"avg":20.4},"humid":{"min":48.2,"max":65.0,"avg":57.1}}
```

Без даних: `count:0`, а `min/max/avg` — `null`. Не обчислюй загальне середнє як просте середнє нерівних груп. Невідомий `period` — `400` з помилкою JSON.
